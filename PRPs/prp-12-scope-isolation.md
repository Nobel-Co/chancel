## The name
**`ringfence`.** Package `ringfence`, CLI `ringfence` with alias `rf`, GitHub `Nobel-Co/ringfence`.
Ring-fencing is the term for a regulatory separation that must hold structurally rather than by policy. Alternate if taken: **`chancel`** — the screened-off part of a church, separated by a physical screen through which the service still carries. Instructions travel, client data does not. Fallback chain: ringfence -> chancel -> parclose.
**Phase 1 gate:** verify availability on PyPI, GitHub, and npm before the first commit. Record the check and the outcome in `decisions.md`.

## Goal
Public, MIT-licensed, forkable Python library and CLI demonstrating one idea end to end: firm-level instructions travel everywhere, client matter data provably never crosses a matter boundary — enforced below the model boundary, so it survives swapping the AI provider. The proof is a test suite deliberately red against the two architectures the industry ships, green against this one, across every provider adapter. Scope is a demonstration: no client data, no tenant management, no UI beyond a CLI.

## The central architectural claim
The wall does not live in the prompt or any vendor SDK. It lives in a provider-neutral policy gate every code path must pass through: every retrieval is a call to `PolicyGate.authorize()`, which takes an `ActiveScope` and proposed target collections and returns an allowlisted set or raises. Nothing reaches a vector store except through it. The Claude Agent SDK `PreToolUse` hook is optional defense in depth for one adapter, not the wall.

## Domain model
A firm has one shared corpus and N spaces, one per matter. A query executes inside exactly one active space; retrieval may read the firm corpus and the active space's corpus, nothing else. Memory tiers: personal (crosses spaces), firm (crosses spaces), matter (never leaves its space). A fact may be promoted matter->firm only if every provenance ID belongs to the firm corpus.

## Store backends
- `isolated`: collection per space + firm collection; gate hands the retriever a fixed allowlist. The claim being defended.
- `filtered`: single shared collection, `space_id` payload, `must` filter every query. The vendor-default pattern.
- `shared`: single shared collection, no filter; system prompt says don't cross spaces. What much shipped software does.

## Provider adapters
ChatModel: anthropic, openai_compat (covers OpenAI/Groq/Together/OpenRouter/vLLM/Ollama via base_url), echo, hostile_echo (scripted adversarial model, deterministic, offline). Embedder: fastembed_local (default), openai_compat, hash_stub (deterministic, offline). VectorStore: qdrant (local/on-disk or server), inmemory (reference implementation, no deps).

- CI green on every PR; demo matrix in job summary; main/develop protected, PR-only

## Known gotchas (verbatim from the PRP)
- Vendor guidance says collection-per-tenant is the WRONG default at scale; this repo departs deliberately and the README must give the reason: it is a SCALING recommendation, and the vendor itself names strict regulatory/compliance isolation as the exception.
- PolicyGate must fail CLOSED. Write the failure branches first.
- No real data, synthetic only, generated by script. CONTRIBUTING.md states this as a PR rejection criterion.
- No provider-specific logic above the adapter boundary; a CI grep enforces this.
- Sparse IDF side channel only reproduces with sparse/hybrid retrieval enabled; skip-with-reason if sparse unavailable, never silently pass.
- fastembed downloads weights on first use; cache in CI; hash_stub keeps unit tier download-free.
- Qdrant local mode holds a filesystem lock; per-test tmp_path fixture.
- Cassettes scrubbed of API keys; pre-commit secret scan over tests/cassettes/ specifically.
- shared mode is EXPECTED to fail; assert the failure so fixing it turns the suite red.

## Leak suite findings
1. Direct canary leak: shared red, filtered green, isolated green.
2. Sparse IDF side channel: filtered red, isolated green (cite vendor doc in docstring).
3. Unrepresentable call: filtered red (constructs and returns data), isolated fails at construction.
4. Deletion verifiability: filtered red — the check cannot be independent of the mechanism.
5. Hostile model: isolated denies all five attacks across all backends/providers, each logged.
6. Gate fails closed: six deliberate breakages, six denies.
7. Promotion gate: Hypothesis property test over generated provenance sets.
Every expected-red result is asserted as red.

## Validation loop
L1 static/hygiene (ruff, mypy --strict, pip-audit, no-attribution grep, no-data grep, abstraction grep) · L2 unit+integration with coverage gates · L3 conformance parametrized across every adapter · L4 leaks + demo · L5 mutmut on policy.py, zero unexplained survivors · L6 cold clone: uv sync && just test && demo, green with no key, no Docker.

## Out of scope
Authentication, RBAC, multi-user sessions, key management, retention, egress DLP, answer-quality evaluation, any UI, any hosted deployment. Named in the README.
